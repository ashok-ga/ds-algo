    Logistics-Flavored (Flexport-y) LLD Problems — Detailed Guide¶

    1) Shipment Tracking Service (per-container & per-leg)¶

    Goal¶

    Ingest shipment Events (ARRIVED, DEPARTED, CUSTOMS_CLEARANCE, DELAY…), keep a canonical current_status, serve timelines and active shipments by port.

    Functional Scope¶

    • ingestEvent(event) idempotently applies events (out-of-order allowed).
    • getCurrentStatus(shipmentId): last known status & location.
    • getTimeline(shipmentId): ordered list of events (with sources).
    • getActiveShipments(portCode): shipments currently at/heading to a port.

    Entities¶

    • Shipment { id, containers[], legs[], currentStatus }
    • Container { id, owner, sealNo, … }
    • Leg { id, mode(SEA/AIR/TRUCK), fromPort, toPort, plannedETD, plannedETA, actualDepartedAt?, actualArrivedAt? }
    • Event { idempotencyKey, shipmentId, containerId?, legId?, type, ts, location, source, payload }
    • StatusAggregator (domain service)

    APIs¶

    interface TrackingService {
  void ingestEvent(Event e);         // idempotent
  CurrentStatus getCurrentStatus(String shipmentId);
  List<Event> getTimeline(String shipmentId, int limit, String afterCursor);
  List<String> getActiveShipments(String portCode, int limit, String afterCursor);
}

    Write Path¶

    1. Dedup by (idempotencyKey) → ignore if seen.
    2. Persist raw event (append-only).
    3. Project: recompute affected leg/container/shipment projections.
    4. Indexes: maintain shipment_current_status, shipment_at_port:{port} sets.

    Storage Schemas¶

    • events(shipment_id, ts, event_id, type, source, leg_id, container_id, payload_json, idem_key UNIQUE)
    • shipment_projection(...)
    • leg_projection(...)

    Concurrency & Idempotency¶

    • Unique constraint on idem_key.
    • Optimistic locking with version.
    • Always derive status from deterministic rules.

    Edge Cases¶

    • Duplicate events, missing legId, conflicting events, timezone normalization.

    Scale Knobs¶

    • Partition events by shipment_id.
    • Cache currentStatus in Redis.
    • Stream processing via Kafka.

    Classic LLD (Flexport‑relevant) — Detailed Guides¶

    This pack covers classic interview LLDs with the depth expected for an SDE‑2 discussion: scope, entities, APIs, persistence, concurrency/idempotency, edge cases, scaling knobs, and a tiny sketch.

    9) Parking Lot (multi‑type, pricing, passes)¶

    Goals¶

    Manage parking spots for different vehicle types, pricing by duration, validations, and receipts.

    Functional Scope¶

    • park(vehicle) → issues Ticket if a compatible Spot is free.
    • unpark(ticketId) → computes fee and frees spot.
    • quote(vehicle, durationHint) → estimate cost.
    • Optional: reserve(spotId, window); monthly Pass with discounts.

    Entities¶

    • Lot { id, name, floors[] }
    • Spot { id, type(COMPACT/REGULAR/LARGE/EV), floor, isOccupied }
    • Vehicle { id, plate, type, isEV }
    • Ticket { id, vehicleId, spotId, entryAt, exitAt?, status }
    • RatePolicy { base, perHour, caps, freeMinutes, evSurcharge }
    • Pass { id, vehicleId, type(MONTHLY/DAILY), discountPct, validFrom, validTo }

    APIs¶

    interface ParkingService {
  Ticket park(Vehicle v, String idemKey);
  Bill unpark(String ticketId);
  Money quote(Vehicle v, Duration hint);
}

    Storage & Indexes¶

    • spot(spot_id PK, type, floor, occupied BOOL, version)
    • ticket(ticket_id PK, vehicle_id, spot_id, entry_at, exit_at, status, pass_id?, idem_key UNIQUE)
    • Index: (type, occupied=false) for allocation; (vehicle_id, status) for active ticket lookup.

    Allocation (Concurrency‑safe)¶

    • Choose eligible spot by type → CAS: 
      UPDATE spot SET occupied=true, version=version+1
WHERE spot_id=? AND occupied=false AND version=?
    • Insert ticket. On failure, retry with next spot.

    Pricing¶

    • Compute duration = exitAt - entryAt
    • fee = base + ceil(hours)*perHour, apply freeMinutes, caps, EV surcharge, and Pass discount; taxes at end.

    Edge Cases¶

    • Duplicate park retries → idempotency via ticket.idem_key.
    • Lost tickets (no id) → match by plate + active ticket.
    • EV on non‑EV spot policy; oversized vehicles.

    Scale Knobs¶

    • Shard by lot; cache “free spots by type” in memory and refresh via DB notify.
    • Event log for audits.

    10) Elevator System (N cars, hall/cab calls)¶

    Goals¶

    Dispatch N elevators to minimize wait and travel time; handle hall (up/down) and cab calls.

    Functional Scope¶

    • hallCall(floor, dir); carCall(carId, floor).
    • Scheduler chooses target queues per car.
    • Modes: normal, peak (up‑collect), off‑peak, maintenance.

    Entities¶

    • Elevator { id, currentFloor, direction, doorState, targets: OrderedSet }
    • Controller (holds all elevators)
    • SchedulerStrategy (interface: assignHallCall(...))
    • Request { floor, dir?, ts }

    APIs¶

    interface ElevatorController {
  void hallCall(int floor, Direction dir);
  void carCall(int carId, int floor);
  void tick(); // simulate time step: move cars, open/close doors
}

    Scheduling Strategies¶

    • Nearest Car (distance + direction alignment + load).
    • Collective Control (serve along direction then reverse).
    • Peak Mode heuristics (favor lobby up calls, parking floors at night).

    Concurrency¶

    • Single controller thread updates cars per tick.
    • If distributed (per bank), partition floors; communicate via message bus.

    Edge Cases¶

    • Overloaded car, door obstructed → reinsert floor.
    • Maintenance mode removes a car; reassign pending requests.

    Observability¶

    • Metrics: avg wait, 95th, energy, door cycles; event logs for replay.

    11) Rate Limiter (Token/Leaky Bucket)¶

    Goals¶

    Limit API calls per key with burst handling and precise windows.

    Functional Scope¶

    • allow(key) → true/false; optionally remaining tokens & reset time.
    • Policies: fixed window, sliding window, token bucket (recommended).

    Entities¶

    • Policy { limit, refillRate, burst }
    • Bucket { tokens, lastRefillTs } (per key)

    APIs¶

    interface RateLimiter {
  Decision allow(String key, Policy p, long nowEpochMs);
}

    Single‑node Design (Token Bucket)¶

    • On allow: refill tokens = max(0, (now-lastRefill)/msPerToken); clamp to burst.
    • Accept if tokens>=1, then decrement.

    Distributed Design¶

    • Store bucket in Redis:
    • Use Lua script to refill + check + decrement atomically.
    • Keys: bucket:{key} with TTL.
    • For sliding window log: ZSET timestamps; trim older than window; count score range.

    Edge Cases¶

    • Clock skew → rely on Redis time (TIME).
    • Hot keys → local warm cache + periodic sync.

    Observability¶

    • Expose headers: X-RateLimit-Limit, -Remaining, -Reset.
    • Counters per policy/key prefix.

    12) In‑memory Cache (LRU + TTL)¶

    Goals¶

    Provide O(1) get/put with LRU eviction and per‑entry TTL.

    Entities¶

    • Entry { key, value, expireAt, prev, next }
    • LRUList { head, tail }
    • Index { Map<K, Entry> }

    APIs¶

    interface Cache<K,V> {
  V get(K key);
  void put(K key, V value, Duration ttl);
  int size();
}

    Implementation¶

    • HashMap + doubly‑linked list for LRU.
    • On get: if expired, evict and return miss; else move to MRU.
    • On put: insert/update, prune expired, evict from LRU if over capacity.

    Concurrency¶

    • Coarse lock or segment locks (striped) for SDE‑2 level.
    • Stats: hit/miss, evictions.

    Persistence Options¶

    • Write‑through to backing store; write‑back with flush timer & shutdown hook.

    Edge Cases¶

    • ttl=0 immediate expiry; huge objects (consider max entry size).
    • Clock jumps → prefer monotonic time.

    13) Logger with Appenders¶

    Goals¶

    Unified logging with multiple sinks (console/file/HTTP), levels, formatting, async batching.

    Entities¶

    • Logger { name, level, appenders[] }
    • Appender (ConsoleAppender/FileAppender/HttpAppender)
    • Formatter (JSON/line)
    • Record { ts, level, logger, message, context }

    APIs¶

    interface Logger {
  void log(Level level, String msg, Map<String,Object> ctx);
  void info(String msg); void error(String msg, Throwable t);
}

    Design¶

    • Synchronous enqueue into a bounded ring buffer.
    • Background worker flushes to appenders (batch, retry with backoff).
    • File rotation (size/time), retention; HTTP adapter with DLQ on persistent failures.

    Concurrency & Backpressure¶

    • If buffer full: drop or block per policy; expose drop counters.
    • Each appender isolated so slow one doesn’t block others.

    Edge Cases¶

    • Recursive logging in appenders → guard.
    • PII redaction in formatter.

    Observability¶

    • Metrics: records/sec, queue depth, error rate per appender.

    14) Notification Service (email/SMS/push)¶

    Goals¶

    Template‑driven notifications across channels with idempotency and retries.

    Entities¶

    • Template { id, channel, body, vars }
    • Message { id, templateId, to, params, status, idemKey, correlationId }
    • ChannelAdapter (Email/SMS/Push providers)
    • Preference { userId, channel, enabled, quietHours }

    APIs¶

    interface NotificationService {
  String send(String templateId, Address to, Map<String,Object> params, String idemKey, String correlationId);
  Status getStatus(String messageId);
}

    Flow¶

    1. Validate prefs & quiet hours.
    2. Render template (engine w/ i18n).
    3. Persist Message(idemKey UNIQUE), status=PENDING.
    4. Enqueue to worker; adapter sends; update status (SENT/FAILED/RETRY/DEAD).
    5. Retries with exponential backoff; DLQ after N attempts.

    Idempotency¶

    • Reuse existing messageId when idemKey duplicates.

    Edge Cases¶

    • Provider timeouts; partial outages → circuit breaker & fallback route.
    • Per‑tenant rate limits.

    Observability¶

    • Traces with correlationId; delivery latency histograms.

    15) Splitwise‑like Expense Splitter¶

    Goals¶

    Track expenses in groups and compute minimal settlements.

    Functional Scope¶

    • addExpense(groupId, paidBy, amount, splits) (equal/exact/percent)
    • balances(groupId) → net per user
    • simplify(groupId) → settlement edges

    Entities¶

    • User { id, name }
    • Group { id, members[] }
    • Expense { id, groupId, paidBy, amount, splits[], createdAt }
    • Split { userId, amount }

    APIs¶

    interface ExpenseService {
  void addExpense(ExpenseSpec spec, String idemKey);
  Map<User, Money> balances(String groupId);
  List<Transfer> simplify(String groupId); // min cash flow
}

    Balances¶

    • For each expense: payer += amount; each split user -= split.amount.
    • balances = credits - debits per user.

    Simplify (Min Cash Flow)¶

    • Greedy:
    • Maintain max creditor and max debtor; settle min(credit, |debt|); repeat until all near zero.
    • For exact minimal edges, use flow/min‑cost, but greedy is fine in interviews.

    Storage¶

    • expense(id PK, group_id, paid_by, amount, created_at, idem_key UNIQUE)
    • split(expense_id, user_id, amount)
    • Index by group_id.

    Edge Cases¶

    • Currency conversion; rounding cents.
    • Member leaves group → freeze old balances.

    Scale¶

    • Group‑level sharding; precompute balances on write; invalidate cache on changes.

    How to present in interviews (quick checklist)¶

    1. Clarify scope/assumptions & constraints (latency, throughput, durability).
    2. Name core entities & invariants; note relationships.
    3. Define APIs (inputs/outputs, idempotency keys, pagination).
    4. Walk write path & read path; call out indexes and consistency model.
    5. Concurrency (locks vs CAS), retries, backpressure, failure modes.
    6. Extensions/patterns (Strategy, Factory, Observer, State), testing hooks.
    7. Close with trade‑offs & evolution plan.
