    Flexport SDE‑2 — High‑Level Design (HLD) Master Pack¶

    A practical, interview‑ready playbook with detailed solutions for 15 systems. Each section gives you: requirements, API, data model, reference architecture, consistency strategy, scaling plan, failure modes, security/PII, and “talk track” bullets.

    Tip: In the interview, spend ~3–5 min on requirements, 5–8 min on architecture, 5–7 min on data/consistency, 3–5 min on scaling+ops, and finish with trade‑offs & evolution.

    1) Global Shipment Tracking Platform¶

    Ingest carrier/webhook/EDI events; dedupe; handle out‑of‑order; project “current status” and serve timelines.

    Requirements¶

    • Functional: ingestEvent, getCurrentStatus(shipmentId), getTimeline(shipmentId), search(shipper, lane, time).
    • SLOs: P99 ingest < 200 ms; query P99 < 100 ms for hot shipments.
    • Scale: 10–50k events/min; 10M shipments active; retention 2 years.
    • Constraints: out‑of‑order events; duplicate sources; multi‑tenant.

    API (sketch)¶

    POST /v1/events {idemKey, shipmentId, legId?, containerId?, type, ts, location, payload}
GET  /v1/shipments/{id}/status
GET  /v1/shipments/{id}/timeline?limit&cursor
GET  /v1/shipments/search?shipperId&port&since&until&page&size

    Data Model¶

    • events(shipment_id, event_id, ts, type, source, leg_id, container_id, location, payload_json, idem_key UNIQUE, created_at)
    • shipment_projection(shipment_id PK, status, last_ts, last_location, last_leg_id, version)
    • leg_projection(leg_id PK, shipment_id, from_port, to_port, planned_etd, planned_eta, actual_departed_at, actual_arrived_at, status)
    • Index: (shipment_id, ts), (port, ts), (last_ts DESC).

    Architecture¶

    • Ingress: API → Kafka topic shipment-events.
    • Dedup: idemKey check (Redis BF + DB UNIQUE).
    • Projectors (CQRS): consume events → update projections (optimistic CAS on version).
    • Reads: API → Redis cache (hot) → projections DB; timelines from events store (append‑only).
    • Storage: events in BigTable/Scylla/Timescale; projections in Postgres; cache in Redis.
    Sources -> API -> Kafka -> Projector(s) -> Projections DB
                               |--> Alerts/SLA Engine
Reads -> API -> Redis -> Projections DB / Events Store

    Consistency & Ordering¶

    • Effectively-once: idemKey + idempotent projection updates.
    • Out-of-order: define event precedence per leg; recompute status from “facts” (dep/arr times).
    • Backfills: separate topic; projector is deterministic & replayable.

    Scaling¶

    • Partition by shipment_id (hash) across Kafka & DB. Cache “hot shipments”.
    • TTL old events → cold storage; compress JSON payloads.
    • Multi‑region: active/active Kafka + DB with regional keys; read local, write dual.

    Failure Modes¶

    • Duplicate events → ignored by idemKey.
    • Poison messages → DLQ with alert.
    • Projection conflict → retry with exponential backoff.

    Security/PII¶

    • JWT + tenant scoping; shipment_id ACLs; audit read access.
    • Minimize PII in payload; encryption at rest; WORM logging for compliance.

    Talk Track Bullets¶

    • Lead with CQRS + event sourcing advantages (auditability, replay).
    • Emphasize idempotency and out‑of‑order handling.
    • Call out hot/cold storage and cache invalidation on ingest.

    2) Real‑time Vessel/Aircraft Location Service¶

    Stream AIS/ADS‑B positions; snap to routes; serve live map + history.

    Requirements¶

    • Ingest: 100k msgs/sec bursts; Serve: 1M concurrent WebSocket clients (fan‑out via pub/sub).
    • Queries: tiles within viewport; history by time window; ship track lines.
    • SLOs: live update end‑to‑end < 2s.

    API¶

    • POST /ingest/positions
    • WS /subscribe?bbox|shipId
    • GET /tracks/{shipId}?since&until

    Data Model¶

    • position(shipId, ts, lat, lon, speed, heading, source)
    • track_summary(shipId, day, polyline, stats) // daily rollups

    Architecture¶

    • Ingest → Kafka → stream processor (dedupe, map-match via route graph) → TSDB (ClickHouse/Timescale).
    • Geo‑index: S2/quadkey for viewport.
    • Serving: WebSocket edge → subscribe to Redis PubSub/Kafka; REST for history.
    • Downsampling: store minute‑level; raw in cold store.

    Scaling¶

    • Partition by shipId.
    • Pre‑tile by zoom-level; CDN for static tiles.
    • Backpressure: drop to last‑known + throttle per client.

    Consistency & Failures¶

    • Latest‑wins by ts; ignore far‑future samples.
    • Gaps → linear interpolate for display.

    3) Milestone SLA & Alerting Engine¶

    Compare planned vs actual; produce alerts with dedupe/cooldowns.

    Requirements¶

    • Evaluate on event arrival & periodic scans.
    • Dedupe per (shipmentId, milestoneType); severity tiers; cooldown windows.

    Architecture¶

    • Stream join MilestonePlan with ActualEvent projections.
    • Rule engine (thresholds/percentiles) → Alerts topic → Alert store.
    • API for GET /alerts?accountId&status.

    Data¶

    • plan(shipment_id, leg_id, depart_by, arrive_by, buffers...)
    • alert(dedupe_key UNIQUE, status, opened_at, severity, meta)

    Notes¶

    • Don’t churn alerts; only escalate severity.
    • Dashboard of open/closed; notification hooks.

    4) Rate & Quote Platform¶

    Compute quotes with tiered rates & surcharges, currency conversion, latency‑friendly cache.

    Requirements¶

    • P95 latency < 100 ms; versioned ratecards; breakdown line items.
    • Multi‑currency; time‑bound validity.

    API¶

    POST /v1/quotes {origin, dest, mode, weight, volume, date, extras[]}
GET  /v1/quotes/{id}

    Data¶

    • rate_card(card_id, lane, currency, valid_from, valid_to)
    • rate_tier(card_id, min_w, max_w, price_per_unit)
    • surcharge(card_id, code, type(PCT/ABS), basis, value, order)
    • quote(id, req_json, items_json, total, currency, created_at)

    Architecture¶

    • Config plane (publish ratecards to edge cache).
    • Stateless compute service (pulls cached configs).
    • Currency cache with periodic updates & fallback.

    Consistency¶

    • Strong consistency at publish (single writer).
    • Eventually consistent caches with version TTL and cache‑busting.

    5) Document Ingestion & Retrieval (PII‑aware)¶

    Store documents; OCR; classify; redact; secure access.

    Flow¶

    1. Upload → content hash → store blob (S3/GCS).
    2. Emit event → OCR/ML pipelines (async).
    3. Index metadata (owner, type, hs‑code, dates).
    4. Redaction: write new derived version; never mutate original.

    Data¶

    • document(doc_id, owner, type)
    • version(version_id, doc_id, parent?, content_hash, labels JSONB, created_at)
    • access_log(doc_id, user, ts, action)

    Security¶

    • Row‑level ACL; signed URLs with short TTL; field‑level redaction policies.

    6) Capacity Planning & Booking Service¶

    Reserve/release capacity per leg; suggest alternates.

    Requirements¶

    • Atomic reservation (avoid double‑booking); overbooking policy; split bookings.

    Architecture¶

    • legs table with reserved_w/v + version.
    • Booking API performs CAS update; then inserts booking.
    • Alternatives via search index by lane/time.

    Data¶

    • leg(id, from, to, cap_w, cap_v, reserved_w, reserved_v, version)
    • booking(id, shipment_id, leg_id, qty_w, qty_v, priority, status, idem_key UNIQUE)

    7) Multi‑stop Route Builder (time‑dependent)¶

    Find best route obeying cut‑offs/layovers/service days.

    Algorithm¶

    • Time‑dependent Dijkstra/A*:
    • Node state: (node, arrivalTime).
    • Edge feasible iff meet cutoff; nextDeparture = schedule.next(arrivalTime).
    • Constraints as pruning strategies (max stops, avoid nodes).

    Data¶

    • node(code, type)
    • edge(from, to, mode, schedule, transit_hours, cutoff)
    • Precompute subpaths for common OD pairs.

    8) Customs Workflow Orchestrator¶

    Human‑in‑the‑loop tasks with SLAs, attachments, audit.

    Architecture¶

    • Task store with state machine.
    • Pull‑based workers; visibility timeouts; retries & DLQ.
    • Metrics by queue/type; escalation policies.

    Data¶

    • task(id, type, ref, state, priority, assignee?, created_at, due_at, attempts)
    • attachment(task_id, doc_id)

    9) Notifications Platform (email/SMS/push)¶

    Templates, preferences, retries, DLQ, dedupe.

    Flow¶

    • send(templateId, to, params, idemKey) → persist PENDING → enqueue → adapter → update status.
    • Preferences & quiet hours checked before enqueue.

    Data¶

    • template(id, channel, body, vars)
    • message(id, template_id, to, params, status, idem_key UNIQUE, correlation_id)
    • preference(user_id, channel, enabled, quiet_hours)

    Ops¶

    • Multi‑provider failover; rate limits; per‑tenant throttles; tracing by correlation_id.

    10) Global Feature Flag Service¶

    Low‑latency evaluation at edge; safe rollouts.

    Architecture¶

    • Control plane: authoring, approvals, audit.
    • Data plane: signed, versioned configs to edge; in‑process evaluators.
    • Targeting: rules (attributes → bucketing via hashing).

    Concerns¶

    • Consistency: eventual across edges; sticky bucketing.
    • Security: sign configs; verify at client; audit changes.

    11) URL Shortener @ Scale¶

    Create/resolve short URLs; analytics.

    Design¶

    • ID generation (Snowflake/flake IDs); or base62 counters per shard.
    • Read path: CDN/edge cache → app → DB; write path: app → DB → cache warm.
    • Analytics via log stream (Kafka) → batch/real‑time sinks.

    Hot‑key Defense¶

    • Per‑key rate limits; negative caching for deleted/expired.

    12) Search Autocomplete¶

    Prefix search on names/ports/lanes with typo‑tolerance.

    Index Choices¶

    • Trie for pure prefix; n‑gram or BK‑tree for edits; elastic/opensearch for production.
    • Ranking by popularity + freshness.

    Serving¶

    • Cache hot prefixes; async refreshers; debounced client requests.

    13) Real‑time Streaming Analytics¶

    Session/window metrics; dashboards.

    Architecture¶

    • Ingest → Kafka → Flink/Spark Structured Streaming:
    • Windows: tumbling/sliding with allowed lateness.
    • State store: RocksDB; exactly‑once sinks to OLAP (ClickHouse/BigQuery).
    • Serving API/BI over OLAP; rollups for long retention.

    14) Distributed Rate Limiter¶

    Global + per‑tenant limits with bursts.

    Algorithm¶

    • Token bucket in Redis with Lua for atomic refill+consume.
    • Keys sharded by hash tags; TTL for idle buckets.
    • Expose headers & trace IDs; fail‑open vs fail‑closed switch.

    15) Object Storage Gateway (S3‑compatible)¶

    Durable object store with versioning and lifecycle.

    Storage¶

    • Data nodes with erasure coding (e.g., 10+4) per region; metadata in strongly consistent store.
    • Versioning; lifecycle (transition to IA/Glacier); encryption (SSE‑KMS).

    API¶

    • S3‑compatible: PUT/GET/DELETE/LIST, presigned URLs.

    Consistency¶

    • Read‑after‑write for new objects; eventual for overwrite unless versioned.
    • Multi‑region replication with per‑bucket policies.

    Capacity & Scale Math Cheats (use as needed)¶

    • Throughput: QPS × avg payload → MB/s; size/day = MB/s × 86,400.
    • Kafka partitions: target ≤ 50 MB/s/partition and ≤ 10k msgs/s/partition.
    • Redis: single shard ~100k ops/s; cluster as needed.
    • Postgres: index fits in memory? aim for working set within RAM.
    • WebSocket: 1M clients ≈ 50–100 nodes (20k/socket/node) depending on infra.

    Observability & Ops Checklist¶

    • Metrics: QPS, p95/p99 latency, error rates, DLQ depth, backlog, cache hit rate.
    • Tracing: end‑to‑end with correlation IDs.
    • Alerts: SLO burn rates; consumer lag; 5xx spikes; saturation.
    • Runbooks: backfill/reprocess, cache flush, rolling deploy, partition rebalancing.

    Security & Compliance¶

    • Least‑privilege IAM; KMS for secrets; audit logs (immutable).
    • PII minimization; data residency; tenant isolation; DLP scans.
    • Input validation, authN (OIDC/JWT), authZ (ABAC/RBAC).

    How to Present (Talk Track Template)¶

    1. Clarify: users, throughput, latency, regions, retention, multi‑tenant needs.
    2. APIs + SLAs: crisp endpoints and SLOs.
    3. Data model: main tables/keys and critical indexes.
    4. Architecture: boxes & arrows; call out queues, caches, datastores.
    5. Consistency: idempotency, dedupe, ordering, backfills.
    6. Scaling: partitioning, cache tiers, read/write paths, hot‑key handling.
    7. Reliability: retries, DLQ, circuit breakers, rollbacks, disaster recovery.
    8. Security/PII: authZ, encryption, audit.
    9. Trade‑offs: why these choices vs alternatives; evolution plan.
